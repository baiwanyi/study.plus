## 修复 server/src/routes/exchanges.ts 兑换/撤销逻辑缺陷

### 识别的问题
1. 🔴 **撤销兑换重复累加余额**：revoke 事务内手动 `balance+=pointsCost`、`basePoints+=pointsCost`，事务外又调用 `recomputeMonthSummary`（基于 point_records 重算），导致返还被计入两次，余额虚高。
2. 🔴 **积分返还实际未生效（隐藏 bug）**：`recomputeMonthSummary` 用 `ne(relatedType,'revoked')` 排除撤销流水。原 revoke 把返还 earn 记录也标 `relatedType:'revoked'`，结果原 deduct 被排除 + 返还 earn 也被排除 → 净变化 0，积分未真正返还。
3. 🔴 **兑换余额不足时误提交 + 双重响应**：`db.transaction` 回调内 `res.status(400).json()` 后 `return` 不回滚事务（空事务仍提交），且后续 `res.json(exchange)` 对已发送响应二次写入，存在 ERR_HTTP_HEADERS_SENT 风险。
4. 🟡 **GET / 无分页**：大表全量返回，性能瓶颈。
5. （顺带修复）Zod 4 无效选项 `invalid_type_error`、TS 2454 `exchange` 明确赋值。

### 修复方案
- revoke 删除手动累加 monthSummary，余额完全交由 `recomputeMonthSummary`（单一事实来源）。
- 返还 earn 记录 `relatedType` 改为 `'exchange'`（非 `'revoked'`），使其被计入 totalEarn，原 deduct 改 `'revoked'` 被排除 → 净返还 +pointsCost（真正返还）。
- 兑换余额不足改为 `throw` 回滚事务，catch 中按 `balance` 字段返回 400，消除双重响应。
- GET / 增加 `limit`（默认 50，上限 200）+ `offset` 分页。
- `z.number()` → `z.coerce.number()` 修正 Zod 4 兼容性；`let exchange!: Exchange` 明确赋值断言。
- 移除不再使用的 `monthSummary` 导入。

- server/src/routes/exchanges.ts（未 git 提交）。

## 修复 server/src/routes/points.ts 积分路由一致性缺陷

### 识别的问题
1. 🔴 **月份汇总重算跑在事务外**：所有 insert 路由（POST /、/by-grade、/by-exam-score、/by-custom-rule）在 `db.insert()` 后调用 `recomputeMonthSummary()`（默认走模块级 `db`，非事务句柄），写入与余额重算非原子；若重算失败，积分已落库但余额未更新。
2. 🔴 **`recomputeMonthSummary` 不支持事务句柄**：内部 `ensureMonthRow` 与 select/sum/update 均用模块级 `db`，事务内调用绕出事务（读不到未提交行）。这是根因。
3. 🔴 **POST /by-grade 等级校验误判**：原 `if (points === 0)` 把「0 分合法等级」与「无效等级」混为一谈（当前默认规则无 points=0 等级，逻辑侥幸成立，但不稳健）。
4. 🟡 **GET / 无分页**：大表全量返回，性能瓶颈（同 exchanges.ts）。
5. 🟡 **GET /advances 无分页**：同上。
6. 🟡 **POST /advances 中 `let advance: PointAdvance` 缺明确赋值断言**：存在 TS 2454 风险（已用 `!` 修复）。
7. 🟡 **advance-helper 中 `repayActiveAdvances` 重算在事务外且有 try/catch 容忍失败**：还款已提交但重算失败则余额不更新。

### 修复方案
- `summary-helper.ts`：`recomputeMonthSummary` 与 `ensureMonthRow` 新增可选 `tx: typeof db`（默认 `db`），内部所有查询改用 `tx`，使事务内调用真正生效。其它调用点传 `undefined` 时行为不变（向后兼容）。注：曾尝试 `Transaction` from `drizzle-orm/libsql` 但 libsql 未导出该符号，最终用 `typeof db`。
- `points.ts`：4 个 insert 路由（POST /、/by-grade、/by-exam-score、/by-custom-rule）将 `insert + recompute` 包进 `db.transaction(async (tx) => ...)`，`recompute` 传 `tx`，保证写入即重算、原子一致。
- `points.ts`：`/by-grade` 改用 `validGrades.includes(grade)` 校验（基于等级是否存在，而非 points===0），更稳健。
- `points.ts`：`GET /` 与 `GET /advances` 增加 `limit`（默认 20 上限 200）+ `offset` 分页。
- `points.ts`：`POST /advances` 中 `let advance!: PointAdvance` 加明确赋值断言，并把 `recompute` 纳入事务。
- `advance-helper.ts`：`repayActiveAdvances` 将 `recompute` 移入事务内（`tx`），删除降级 try/catch。
- `exchanges.ts`（连带修复）：把事务**外**两处 `recomputeMonthSummary(currentMonth)` 移入事务并传 `tx`（之前修复时遗留的不一致），保证兑换/撤销与余额原子一致。

- `server` 包 `tsc --noEmit` 通过（EXIT:0）。

## 直接审查与修复 server/src/routes/advance-helper.ts

### 识别的问题
1. 🔴 **`loadSystemSettings` 的 `JSON.parse` 健壮性**（L15-35）：`JSON.parse(rows[0].value)` 未校验 `value` 类型。`options.value` 列可空/可能为数字，`JSON.parse(undefined)` 抛错被静默吞掉回退默认，`JSON.parse(数字)` 返回数字被 `typeof object` 拦掉回退默认——掩盖配置错误。
2. 🔴 **`isFirstDayOfMonth` 时区错位**（L37-39）：用本地 `new Date().getDate()` 判断月初，但系统时间基准是 UTC（monthSummary 用 UTC 年月、createdAt 存 UTC）。东八区存在 8 小时错位，定时还款任务可能重复/漏触发。
3. 🟡 **`repayActiveAdvances` N+1 循环**（L70-111）：逐条 advance insert+update，数量大时慢；但 advance 通常个位数，标 minor，未改。
4. 🟡 **`calculateAdvanceRepayment` 余数**（L41-62）：Math.ceil 致 totalRepayment 略高于 baseRepayment，是有意利息取整设计（下游依赖等式），非 bug，仅标注不改。

### 修复方案
- `loadSystemSettings`：增加 `typeof rows[0].value === 'string'` 前置守卫，非字符串直接回退默认，避免 JSON.parse 异常被静默吞掉。
- `isFirstDayOfMonth`：改用 `new Date().getUTCDate() === 1`，与系统 UTC 时间基准一致。
- **连带修正 `summary-helper.ts` 类型**：`recomputeMonthSummary`/`ensureMonthRow` 的 `tx` 参数原用 `typeof db`，但 `db.transaction` 回调 `tx` 是 `SQLiteTransaction`，赋值不兼容（TS2345）。改为联合类型 `DbOrTx = typeof db | (Parameters<typeof db.transaction>[0] extends (tx: infer T) => unknown ? T : never)`，同时接受主库与事务句柄，默认值 `db` 仍成立。注：曾误用 `drizzle-orm/libsql` 的 `Transaction`（未导出）和纯 `typeof db`（不兼容事务 tx），最终用联合类型 + Parameters 提取解决。

### 验证
