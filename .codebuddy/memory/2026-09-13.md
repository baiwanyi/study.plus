# 2026-09-13

## 修复 AI 输出「非合法 JSON」导致的 Invalid preview analysis response format
- 现象（与 09-12 的截断问题不同源）：`AI preview analysis error: Invalid preview analysis response format`，`safeJsonParse` 报 `Unexpected non-whitespace character after JSON at position 24`，rawLength/repairedLength 均为 868。
- 关键证据：模型返回体开头是请求参数 `{"type": "json_object"}`，其后字段顺序错乱（strengths → completenessComment → completenessScore），并夹杂游离字符串片段。即模型把请求里的 response_format 值回显进了正文、整体输出退化，属于模型侧偶发行为，不是 token 预算问题（该调用 max_tokens 已为 6000）。
- 改动（`server/src/services/ai/core.ts`，单文件）：新增 `isParseableJson()`（解析口径与 `safeJsonParse` 一致：先原文直解，再按围栏/控制字符容错，失败时不打日志避免刷屏）；JSON 模式下新增 `invalidJson` 判定（内容非空、非截断、但整体不可解析），纳入统一重试（与空响应、截断并列），标签 `[DeepSeek Invalid JSON]`，按原参数重新采样（截断才扩容）；重试耗尽时打印 `content_head` 等诊断并抛出「响应不是合法 JSON」的明确错误，不再让下游误报为格式错误。
- 三类可自愈故障现统一在 `callDeepSeek` 内退避重试（1s/2s/4s，上限 3 次）：空响应、JSON 截断（自动扩容 max_tokens）、JSON 输出退化。
- 验证：server `tsc --noEmit` 通过、`read_lints` 无报错；`vitest run studynotes preview-quiz` 7/7 通过。
- 未采取的方案：不在重试时移除 `response_format` 做降级（其余 3 个 AI 服务文件同样使用该参数且调用稳定，判断为偶发退化而非字段不被支持）；不引入按字段抽取的「残缺 JSON 抢救」，避免把错乱数据静默入库。

## 追加：把「结构校验」纳入 core 重试（解释日志里只有「重试 1/3」的原因）
- 新现象：日志出现 `[DeepSeek Invalid JSON] 重试 1/3` 后紧接 `AI preview analysis error`，但**没有**「重试耗尽」、也没有 2/3、3/3。
- 推断（成立）：重试后的第 2 次响应是「语法合法但结构不符」的 JSON，core 判定成功直接返回，失败发生在调用方的字段校验环节，因此 core 的重试链路只走了 1 次。关键结论：**语法合法 ≠ 可用**。
- 改动（`core.ts`）：`CallDeepSeekOptions` 新增可选 `validateJson?: (parsed: unknown) => string | null`（null 通过，字符串为不合格原因）；`isParseableJson` 改造为 `parseJsonLoose(): JsonParseOutcome`（返回解析结果而非布尔）；新增 `schemaError` 判定与 `unusableJson` 聚合，重试条件从「语法非法」扩展为「语法非法或结构不符」；JSON 不可用时不再盲重试，而是回传上次输出（截断至 1200 字符）作为 assistant 消息并追加 `buildJsonCorrectionHint()` 纠偏提示；日志新增 `[DeepSeek Schema Mismatch]` 标签，耗尽日志含 `syntax_error` / `schema_error` 字段。
- 改动（`studynotes.ts`）：新增 `validateEvaluationShape()`、`validatePreviewShape()`，分别作为 `evaluateStudynotesReflection`、`analyzePreview` 的 `validateJson` 传入；调用方原有字段校验保留作二次防线。
- 验证：server `tsc --noEmit` 通过、`read_lints` 无报错；`vitest run studynotes preview-quiz` 7/7 通过。
- 结论备忘：core 只管「语法」、调用方只管「结构」的分层会让 core 误判成功、重试形同虚设；后续新增 JSON 类 AI 调用应一律通过 `validateJson` 声明结构。

## 追加 2：修复纠偏重试引发的请求超时（默认 30s 单次超时被打爆）
- 新现象：`AI preview analysis error: The operation was aborted due to timeout`。
- 根因：`analyzePreview` 未配置 `timeoutMs`，落到 `callDeepSeek` 默认 30s；而带纠偏提示的重试请求更长（含上次输出 1200 字符），推理耗时增加，单次请求被 30s 中断。原实现中超时错误直接冒泡，信息不可读（英文 DOMException）。
- 改动（`core.ts`）：新增 `DEFAULT_ATTEMPT_TIMEOUT_MS`(30s)、`TOTAL_BUDGET_MS`(120s)、`MIN_ATTEMPT_BUDGET_MS`(5s)；`callDeepSeek` 增加内部参数 `deadlineAt`（首次计算截止时间、重试时透传，整条链共享）；单次超时取「配置值」与「剩余预算」的较小值；重试条件增加 `hasBudgetForRetry`，预算不足即不再重试；fetch 段包 try/catch，把 `TimeoutError` 转成中文错误（含单次上限与总预算）。
- 改动（`studynotes.ts`）：`evaluateStudynotesReflection`、`analyzePreview` 增加 `timeoutMs: 60_000`。
- 验证：server `tsc --noEmit` 通过、`read_lints` 无报错；`vitest run studynotes preview-quiz` 7/7 通过。
- 遗留（未动，超出本次改动范围）：`weekly.ts` 的 JSON 调用仍未显式设置 `timeoutMs`，默认 30s，存在同类超时隐患。
- 观察：用户日志中「重试 1/3」之后未再出现格式错误，说明「回传上次输出 + 纠偏提示」的重试确实把首轮退化纠正了回来；当前主要残留问题是首轮退化率偏高（模型侧行为）。

## 追加 9：怀疑网关对 response_format 处理异常，先对分析与评估停发该参数
- 现象：换模型（deepseek-flash）并收紧提示词后，日志仍是清一色「[DeepSeek Invalid JSON] 重试 1/3，等待 1000ms」，即**首次请求几乎必然失败**、靠重试救回，不像偶发退化。
- 证据链：最早一批日志中模型输出的开头是 `{"type": "json_object"}`——正是请求体里 `response_format` 的值，说明该网关把参数混入了模型可见内容，模型顺势复读，首轮 JSON 必然非法。
- 改动（`core.ts`）：`expectsJson` 与「是否发送 response_format」解耦——`Boolean(validateJson) || response_format?.type === 'json_object'`，使调用方可以只声明 validateJson 而停发该参数，同时仍享有 JSON 校验、截断检测与纠偏重试；重试日志追加响应诊断（`content_length` / `content_head` / `schema_error`），便于下次直接看到退化形态。
- 改动（`studynotes.ts`）：`evaluateStudynotesReflection`、`analyzePreview` 停发 `response_format`（注释已记录原因），JSON 约束由提示词 + validateJson + 纠偏重试保证。
- 未改动（仍发送 response_format，待验证后再决定）：`weekly.ts` 周报分析、`task.ts` 作业评分、`studynotes.ts` 的客观题出题 / 测验批改 / 预习问答生成 / 预习问答批改，共 6 处。
- 验证办法：重跑预习分析，若 `[DeepSeek Invalid JSON]` 消失即假设成立（首轮不再退化），随后可统一移除其余 6 处；若仍出现，新日志会带 `content_head`，可据此精确定位。
- 退路：该改动仅一行，恢复 `response_format` 即可回退；即使模型输出 markdown 围栏或解释文字，`safeJsonParse`（剥离围栏 + 取首尾大括号）仍可解析。
- 验证：`read_lints` 无报错；server `tsc --noEmit` 通过；全量 `vitest run` 35/35 通过（7 个文件）。
