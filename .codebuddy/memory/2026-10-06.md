# 2026-10-06

## 修复 DeepSeek JSON 截断重试策略无效（输出长度不随 max_tokens 增长）
- 现象：日志连续出现 `[DeepSeek Truncated] 重试 1/3，由 6000 扩容至 9000`、`重试 2/3，由 9000 扩容至 13500`，且夹杂一次 `content_length: 0` 的空响应，来源为 `notes-evaluate`（学习心得评估）。
- 关键证据：请求 `max_tokens` 为 6000/9000，但 `finish_reason=length` 时 `content_length` 仅 436~1246 字符（中文约 1 汉字 ≈ 0.6 token，即 300~800 token），与上限差一个数量级；且**扩容后输出反而变短**（6000 → 1246 字符，9000 → 486 字符）。说明 `length` 并非撞我们请求的上限所致，可能由网关/模型把推理 token 计入同一预算或上游另有更小硬限制造成 —— 原「扩容 max_tokens」策略在该环境下物理上不可能成功，只会白等1s/2s/4s 并白烧3 次调用，把 120s 总预算耗尽。
- 改动（`server/src/services/ai/core.ts`）：新增常量 `MAX_TRUNCATION_GROWTH`(1) 与内部状态 `TruncationState { growCount, hintAttached }`，`callDeepSeek` 增加第 4 个内部参数 `truncationState`；重试条件从 `truncated && canGrow` 放宽为 `truncated`，但**扩容次数受限**——首轮截断扩容一次并附加精简约束，其后不再扩容、只靠精简约束重试；新增 `buildTruncationHint()`（评语 ≤40 字、每数组 ≤2 条且每条 ≤30 字、无内容给空值）；重试日志与耗尽日志补`model` / `max_tokens` / `prompt_tokens` / `completion_tokens`，并新增 `content_tail`（截断点在尾部，打 head 看不出断在哪个字段）。
- 改动（`shared/src/constants.ts`）：`defaultPromptEvaluateStudynotes` 重写为多行拼接并补齐「输出要求」（只输出一个 JSON 对象、评语类字段 ≤60 字、`missingPoints`/`improvementSuggestions` 各 1-3 条、`errors` ≤2 条、每元素 ≤40 字）；`promptAnalyzePreview` 补「数组内每个条目不超过 40 字 + 只输出 JSON 对象」。
- 改动（`server/src/services/ai/studynotes.ts`）：`evaluateStudynotesReflection`、`analyzePreview` 的`max_tokens: 6000` 注释同步为「常态预算，仍截断时由 core 扩容一次并附精简提示重试」，说明扩容已不是兜底手段。
- 失败文案：`core.ts` 截断耗尽错误由「被max_tokens 截断且无法继续扩容，请精简输入或提升上限」改为「被中途截断且已精简重试 N 次仍未完整，请稍后重试或缩短内容后重试」（原文案在无扩容空间时才成立，现已不准确）。
- 验证：server `tsc --noEmit` 通过、`read_lints` 无报错；`pnpm test` 全量 7 文件 35 用例通过。
- 未采取的方案：不改`ai_usage_logs` 表新增 `finish_reason` 字段（需DB 迁移且前端无消费方，收益低）；不调整 `max_tokens` 数值（证据表明数值不是瓶颈）；未落库截断率统计，改为先在日志中观察 `completion_tokens` 与 `max_tokens` 的差距。
- 遗留观察点：修复后需看真实日志中 `completion_tokens` 是否接近 `max_tokens`——若接近，说明是推理 token挤占预算，应改为显式指定非推理档位（`DEEPSEEK_MODEL_ANALYSIS`）或进一步下调单次输出规模；若远小于而`finish_reason`仍为 `length`，则是上游/网关异常中断，需换网关或换模型排查。
